## #42 / #19 / #113 — fixed 2026-08-05

#42 mask check mark stuck ON. `updateCarriedMask` derives the carrier's
clothing-active state from `scanSaysWorn || latchSaysWorn`, where the scan reads
the ped's face components and the latch remembers which way WE last toggled it.
The line `if (scanSaysWorn) maskWornRouteLatch = selectedRoute;` re-armed the
latch from the scan unconditionally. The face component is not stripped until
the MASK_OFF interaction finishes, so throughout that animation the scan still
read worn and kept rewriting the latch back to worn — undoing the `-1` latched
at `START_ITEM_INTERACTION`. Once the component finally cleared, scan=false but
latch=true, and the OR held INVENTORY_SET_CLOTHING_ACTIVE true forever.
FIX: gate the re-arm on `ourMaskInteractionInFlight`
(`ITEM_INTERACTION_RUNNING(maskPed) || now < maskSelfEquipUntil`). During the
take-off the mark still shows (scan is legitimately true); after it, both agree.

#19 wagon horse cores. The drain loop (GET_DRAFT_HORSE slots 0-5, SET_CORE) was
correct and running. The report was a DISPLAY gap: the core HUD only swaps to
the horse when mounted, never for a wagon.
`HUD::_SHOW_HORSE_CORES` (0xD4EE21B7CC7FD350) / `_SHOW_PLAYER_CORES`
(0x50C803A4CD5932C5) are what Rockstar's own shop and satchel scripts use.
Two-horse question, answered rather than fudged: there is NO native to retarget
which horse the display tracks — searched the PED namespace and the full script
corpus; it always follows the player's own horse. So the swap is gated on the
tracked horse (`GET_OWNED_MOUNT` else `GET_LAST_MOUNT`) actually being one of
the wagon's hitched horses. Justification for treating one horse as the team's
reading: every hitched horse receives the identical `drain` value per tick in
the same loop, so they tire at the same rate. If the player's horse is not in
the harness the display stays on player cores rather than showing an idle
animal. New `[WagonCores] ShowHorseCores` (default 1).

#113(a) "only the first coyote tagged". The nearby-candidate loop in
`updateReconTagging` filtered on existence, distance, projected extent and LOS
but NOT on `isReconTagged`. Selection picks the candidate nearest screen centre,
so a freshly tagged animal usually stayed the winner and the scan never advanced
to untagged pack-mates. Consistent with both of Lexer's observations: the
away/out cycle helped because it cleared `observed`, and the free-aim path
worked because `GET_ENTITY_PLAYER_IS_FREE_AIMING_AT` selects the pointed-at
entity and bypasses the nearest-to-centre rule. FIX: skip tagged candidates.
