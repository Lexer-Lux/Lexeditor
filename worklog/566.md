# #566 — Make the interface usable with a controller

## Requirement

Drive Home, every plugin editor, Settings, dialogs and the Data Map with a
controller alone. Required before the Steam Deck download (#496). Build it
once in `ui/framework.js` on the browser Gamepad API.

## Implementation (branch `claude/controller-navigation-566`)

- `ui/framework.js` gets a `gamepad` block, exported as
  `LexeditorUI.gamepad`, that every page loading the shared UI runs,
  including Home.
  - Movement: the D-pad or left stick (threshold 0.55) moves focus to the
    nearest visible control in that direction. Off-axis distance is weighted
    3×. Holding repeats after 380 ms, then every 110 ms.
  - Scope: movement stays inside the topmost open dialog
    (`.lex-dialog-backdrop`, `[role=dialog][aria-modal]`, Home's `#modal`) or
    open `[role=menu]`.
  - A clicks the focused control and toggles checkboxes. On a text field, A
    starts typing and asks the host for the Steam keyboard; the D-pad then
    stays in the field until B.
  - B sends Escape. If nothing closes, the top dialog's close button is
    pressed; otherwise B goes back through the editor's navigation history.
  - Left and right step range and number inputs within their bounds, and
    move to the next or previous option in a select.
  - LB and RB cycle `nav button[data-tab]`, wrapping around. LT and RT press
    the nearest `.lex-pager` Previous/Next page button.
  - The `lex-gamepad-active` class draws a 3 px highlight ring
    (`ui/framework.css`). Any mouse movement clears it.
  - Only `mapping === "standard"` pads are read. Polling runs only while a
    pad is connected.
- `ui/editor-host.js`: the editor iframe gets `allow="gamepad"` (it is
  cross-origin to Home). Home stops reading the pad while an editor frame is
  open.
- `desktop_host.py`: `show_on_screen_keyboard()` runs
  `xdg-open steam://open/keyboard` only when `SteamDeck=1` or `SteamOS=1`;
  elsewhere it does nothing.

## Evidence (agent-side only)

- `tests/test_gamepad_navigation.py` drives a scripted standard pad through
  `navigator.getGamepads` in headless Chromium. It covers spatial movement,
  stick repeat, the focus ring, A/B in and out of a dialog, value adjust at
  bounds, tabs and pages, text entry with the keyboard request, the frame
  handoff, and Home card focus and open.

## Unverified / next work

- Real hardware: WebView2 on Windows, and WebKitGTK on SteamOS, which may
  need libmanette for Gamepad API support. Nothing was tested on a Deck.
- `steam://open/keyboard` as the way to raise the Deck keyboard from a
  desktop-mode app is unconfirmed.
- Editor-specific widgets built from non-focusable elements (canvas curve
  editors, drag reorder, tree graphs) are reachable only through their
  focusable parts.
- Rendered check across plugins at small windows and large UI scales has not
  been done.
- Lexer test: on the Deck or with a pad on Windows, walk Home → a game → tabs
  → a list page → a field → a dialog, and report any control focus cannot
  reach.
