### Code evidence

- All 33 Warband Data Map rows have an explicit capability regression.
- Structured Module System saves preserve record IDs and unmodeled fields, reject
  stale source, create backups and replace atomically. Misc. datasets reject
  ambiguous duplicate stable IDs; Items and Troops use source record indexes so
  pre-existing duplicate game IDs remain distinct and unchanged.
- Items and raw source saves also use source hashes, stale-write refusal,
  backup and atomic replacement. Item IDs are fixed because cross-file
  references are not rewritten.
- Helper-generated records are not treated as literal tuple records. Public
  Persistent World particle records using psys(...) are therefore source-only.
- Older fixed tuple shapes are also fail-closed: a synthetic 22-field particle
  regression matches the legacy shape found in Native++ and Rome at War and is
  refused by structured saving rather than padded or guessed.
- Installed module discovery is based on each module.ini, not optional manuals.
- The game-inspired CSS theme contains no game artwork. Installed Warband font
  data is read locally into the user's private cache; no TaleWorlds font or sound
  asset is committed.

### Flat Module System project import evidence

- Find/select now recognizes a flat source root or a repository root containing
  one unambiguous child named like `Module System`.
- The selected public source is fingerprinted and copied into a content-addressed
  managed project; source symlinks, oversized trees and ambiguous layouts are
  rejected. The original folder is never written.
- Only the managed copy's literal `module_info.py export_dir` is rewritten to
  `../Module/`. A generated wrapper build accepts only upstream
  `python[.exe] <script>` steps, verifies each referenced script exists, drops
  display/pause/restart commands and rejects every unknown batch command.
- Re-selecting an unchanged source reuses the same managed project instead of
  recopying it, so existing Lexeditor edits are preserved.
- The regression fixture mirrors pinned Persistent World
  `a35fd5d89cbb4e684ddf2fe4a6de9fe5066b9988`'s flat root,
  `export_dir="../PW/"` and `python -tt build_module.py` build shape. It
  performs two sequential edits to the same imported item record, proves the
  second preserves the first plus unrelated records/comments/backups, re-selects
  the original source and proves the managed edit survives, while the original
  source files remain byte-for-byte unchanged.
- Direct read-only checks of the pinned public Persistent World, Native++ and
  Rome at War repositories found one literal `export_dir` in each and no
  unsupported/missing Python build step under the importer allowlist. Native++
  and RaW hard-coded game export paths therefore become local only in the copy.

### Isolated candidate boundary

Never use C:\Lexeditor as a disposable candidate. The Warband workflow now
checks out the literal pull-request head rather than GitHub's synthetic merge
ref. Its Windows candidate job stages that exact source into a separate folder,
generates Run-Warband-Candidate.cmd, bootstraps a private .venv, runs
tools\Warband-checks.cmd --checks-only from the staged folder, removes the test
venv, and uploads warband-candidate-<head>.zip.

The candidate launcher intentionally bypasses repository install.ps1 because
that shared installer still targets C:\Lexeditor. The candidate requires a
working Python 3 launcher/interpreter and network access for the first pip
install. A passing candidate job proves the isolated source package and
bootstrap path, not installed Warband, Steam or WSE2 gameplay.
