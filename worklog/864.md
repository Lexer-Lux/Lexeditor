# 864 — Tool Belt (DS1)

Dark Souls III-style tool belt as a DS1 tweak mod. Issue stays
`actionable`: slice 1 is lab-verified, the native slice is designed with
grounded leads but unproven.

## Requirement

Backport Dark Souls III's Tool Belt concept: a dedicated belt separate
from the normal quick-item cycle, holding eligible utility and frequently
used items, with the quick-item bar and cycling preserved, belt access
distinct from the pouch tweak (#861) so both coexist, and controller and
keyboard equivalents.

## Static findings for slice 2

- Quick items are rawSlots 15-19 (loop at 0x495D00, `cmp ebx, 5`); full
  map 0-3 weapons, 4-7 ammo, 8-11 armor, 12-13 rings, 14 reserved.
- Selections at equip+0x8C/+0x90 (hands), +0x94/+0x98 (arrows),
  +0x9C/+0xA0 (bolts). The use path reads each slot twice: live at
  equip+0x24 and saved at assembly+0x24, plus the actor assembly at
  player+0x840. The island must write all three and restore them.
- Equip-change shape at 0x7468CB (live write + notify 0x31B540);
  weapon/ammo use bound `cmp ebx, 7` at 0x749B91; quantity translators
  0x747860/0x747920 carry no quick codes.
- HUD: `F20-00_item` (icon + count) under `F20-00` with the
  `text_item_name` popup; frame hook 0x39761A shared with every input
  tweak. Pad commits at +0x86/+0x87/+0x92 are unidentified.
- DS3's belt (separate equipment slots for multiplayer/utility items,
  start-menu access, 10 quick slots left free) confirmed from player
  docs; no belt/pouch names exist in any of the three exes, and none of
  DS2 Scholar's 45 menu classes hints at a belt, so the backport
  reimplements the concept natively. See the mod `sources.md`.
- Unmapped: selected-quick field, Use-Item (X) and d-pad pad bytes,
  quick-use consumer, keyboard routing, belt-strip placement,
  multi-frame use timing. Two dataflow scans came back empty: no
  selection access through an inline-derived equip register (779 unique
  game-data sites), and no actor-assembly (+0x840) selection access
  through an inline-derived world chain (2174 refs). The switch path
  takes its pointers as arguments; map it live.

## Live mapping (2026-10-10/11, offline, Debug mode, read-only probes)

- Quick slots are FIVE dwords at `equip+0x1B8..0x1C8` holding INVENTORY
  INDICES (`-1` = empty); a mirror copy sits at `equip+0x60..0x70`
  (trailer `+0x74` stays 0). His bar read `[77, -1, 94, 82, 121]`.
- The selected quick item is mirrored at `equip+0x1CC` (dword). A 10-tick
  scroll burst flickered it `...82 -> 121 -> 77 -> 121`, cycling only
  the four non-`-1` slots (the game skips empties, no 0-4 index found).
  Values confirmed as indices, not goods ids: none of 77/82/94/121 is
  in the 95 isEquip==1 goods (eligible ids start at 100).
- L-select `equip+0x90` flips 0->1 live. No selection field exists in
  actor+0x0..0x400 (only timers/flags churn there). `+0x1CC` also moved
  with older switch traffic, so weapon-switch exclusivity is unproven.
- Keyboard facts from his binds: Use = R, weapon switch = Down-arrow +
  mouse, item/magic switch = wheel directions. Still needs mapping:
  Use byte, direction bytes (fresh X1 per launch; heap moves every run:
  pad bases 0x11D069D0, 0x11D1F9B0 seen), quick-use consumer.
- Recorder: `probe_864_watch.py` (equip+actor 1/s, relaunch-proof) plus
  `analyze_864_timeline.py` (runs, steps, burst transition counts).
  One zombie recorder wrote 420 stale-base pad dumps; deleted, 185
  valid run-1 pad dumps kept.
- Slice-2 bake design: `tweak.py build()` keeps emitting
  `layout/tool-belt.json` and adds `native/tool-belt.json`
  (`exe_patches.validate` spec v2: one island + hooks). The island
  bakes the five validated goods ids, resolves each owned id to its
  inventory index by scanning the live tables (no heap constants),
  and runs swap-use-restore over a borrowed quick rawSlot. Still
  open: gesture/use hook site (needs X1 + hold script), restore
  protocol across the three assemblies, belt-strip placement.
- Island code convention (from stamina): hand-written GAS Intel-syntax
  `.S` + `.ld`, tests rebuild with binutils when available, settings
  patched into baked tables like FACTOR_CODE. The belt island stays
  unwritten until the gesture hook site is mapped (entry/ABI unknown);
  the inventory-scan leaf (goods id -> index) is fully specified and
  goes in first once the site lands.
- Belt strip plan: up to 64 layout nodes allowed; text nodes carry
  {dialog,name,lookLike,dy,length} and sprite nodes add a
  [dialog,node] source plus color. The strip is five sprite nodes
  near the quick bar; their icon caches update at runtime from the
  island (widget +0x22C pattern), since static nodes cannot show
  per-belt icons. Placement and widget update are unmapped and need
  a live look after the gesture lands.
- Inventory path verified live (`probe_864_inv.py`): rawSlots[15..19]
  at `equip+0x24+s*4` == the +0x60 copy; count `+0x130` (2048), split
  `+0x140` (64), tables `+0x150/+0x158`; entries 0x1C bytes with flags
  `+0` (0x40000000 on goods), goods id `+4`, quantity `+8`. His live
  entries read ids 207/100/106/330, qtys 13/1/1/26, all four in the
  95 eligible. The island can scan id->index with no heap constants.

## Risks

- The mark sits over the item name, left of the star; overlap with long
  names or the star needs the in-game look.
- Swap-use-restore across three assemblies is unproven; multi-frame
  uses (estus drinking) may read the slot after an early restore.
- The hold gesture is undecided (hold-Use vs hold-Down); pick it with
  the pouch gesture so the two never collide.
