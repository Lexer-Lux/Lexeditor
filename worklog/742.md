# 742: Mana System

## Requirements

DS1 mana-system tweak as the technical foundation for replacing spell
usages with mana: mana pool + bar UI, per-spell costs, global X/N
derivation from vanilla usages, per-spell override property, optional
weapon-skill durability-to-mana toggle, usage-to-mana UI and
description updates, vanilla behavior when disabled, and the
hooks/data paths for the separate design issue. Runtime dependency on
the Estus rework (#723) for Ashen Estus restoration, not an issue
blocker.

## Exe survey (static, unproven hook candidates)

Vanilla exe (`pre-doa-backup`, 50,286,344 bytes, matches the repo's
known size). 360 unique magic/attune/cast/spell strings; Havok and
Clang test noise excluded. Probes: `probe_mana_exe.py`,
`probe_mana_xref.py`, `probe_mana_disasm.py` in `C:\tmp\lexeditor-dev\`.

- Event-command stubs, all the same 78-byte shape (singleton fetch,
  then `call [r10+0x58]` with the command name in r8): the real
  logic sits behind that dispatch. GetCurrEquipMagicID @0x2b7c0,
  ChangeEquipMagic @0x2d7f0, GetEquipMagicIndex @0x2c210,
  CastPointSpell @0x1bed0, CastTargetSpell @0x1c010,
  SetMagicGameDataStateForEvent @0x1df00. ACTION_Equip_ChangeMagic
  is referenced once at 0xae0b inside a 3 KB function. Dynamic
  target: break on these stubs and follow the dispatch to the cast
  path and the count decrement.
- Attunement-menu registration (dialog-name pointer stored at
  singleton+0x38/+0x40): FrpgMenuDlgMagicEquip @0x342c0 and
  @0x6faf40, FrpgMenuDlgSpellTab @0x320b0 and @0x69dd60,
  FrpgMenuDlgSpellPlate @0x32020 and @0x69d390. The usage-count
  display code lives near these singletons: the presentation-hook
  neighborhood.
- Related strings with no direct xref yet: CastPoint/CastTarget
  Plus and Horming variants, OnLeaveMagic, OnReviveMagic,
  MENU_TEXT_EFFECT_TYPE_MagicRevived.
- Vtable RTTI names the singletons (probes `probe_mana_init.py`,
  `probe_mana_vtable.py`): the 0x2xxxx stubs serve
  `AiScript::NS_FRPG` (vtable 0x138ee90), the 0x1xxxx stubs serve
  `FrpgEventProxy::NS_FRPG` (vtable 0x1362e00), and the menu
  singletons are `FrpgMenuDlgSpellTab` (0x13b7bb0) and
  `FrpgMenuDlgMagicEquip` (0x13c9458). Every slot 0x58 lands on the
  same shared DLRF dispatcher at 0xd55d50, which calls 0xd56e20.
  So a breakpoint at 0xd55d50 with the command name in r8 catches
  all magic event traffic; the per-command stubs above are the
  narrower alternative.
- The invoke behind the dispatcher (0xd56e20, probes
  `probe_mana_invoke.py`, `probe_mana_methods.py`) walks 0x20-stride
  method tables of {impl, name, length}, length-sorted, then follows
  a base-class chain. But every command-name string has a single
  instance with zero data refs: the tables are built at runtime, so
  per-command implementations are only visible in a live process.
  Static RE stops here; the dynamic entry points above are the
  next step.
- Caveats: the LEA scan is pattern-based, so any xref can be a
  false positive (OnReviveMagic's falls outside .pdata and likely
  is one); neighbor "code pointers" were ASCII junk from packed
  string tables. Singleton pointers live in BSS (runtime-created).
  None of this is a proven hook.
