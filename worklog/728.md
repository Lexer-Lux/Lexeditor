# 728 — UI Rework (DS1 grid-style lists)

Owner: Muse (branch `ds1-728-ui-rework`, worktree `lexeditor-728`).
Issue scope: audit DS1's cramped list UIs, identify DS2/DS3 grid patterns,
recreate them in DS1 behind a tweak, preserving behavior.

## What the audit found (evidence in scratchpad `ui728/`)

- DS1 list screens are 14-row text lists: `list_main` / `list_category` /
  `list_insert` hold `button0_0`..`button13_0` (dynamic text, 30 units apart)
  plus `cursor0_0`..`cursor13_0` highlight rects. `audit_geometry.txt`.
- Row-content templates (`list_arms`, `list_armor`, `list_item`,
  `list_magic`, `list_arrow`) are single name-plus-stat-column layouts the
  exe instantiates per row; the exe references those dialog names as wide
  strings, and formats row names with `button%d_0` / `cursor%d_0`.
- `T02_equip_list` (equipment loadout) is already a 2D icon-button grid with
  exe-driven 2D navigation — not a rework target.
- DS2 is NOT available: both installs on D: are gutted (0 bytes besides a
  config). DS3 is present (24.8 GB) but packed in Data0-5/DLC `.bdt`/`.bhd`
  archives with no extractor on this machine, and its menu tech differs
  anyway. So "copying from DS2/3" reduces to design reference; all
  implementation is DS1-native.

## Technical conclusion

A working grid needs two things: (1) reposition existing row nodes in the
DRB layout, (2) exe patches to list navigation (2D cursor, scroll stride).
(1) is done on this branch: `menu_layout.py` moves plus the `ui-rework`
scaffold (28 moves, `list_main` column-major). (2) is next: find the
`button%d_0` user (capstone-assisted RE), loop bound and cursor math.

## Navigation RE findings (static, RVAs in the fingerprinted exe)

- `find_child` 0xED6020 has 1,182 call sites; the name arrives via
  `lea rdx` (832 static names incl. `cursor0_0`..`cursor5_0`,
  `button0_0`..`button5_0`, `scrollbar`, `list_cursor`) or stack-built
  (123 dynamic sites, incl. a 0x63Cx cluster). 227 pass it in a register.
- Row binder 0x63C2C0 (no direct callers; virtual): formats a dynamic node
  name through 0xC5C00 with the row index in r8d, calls `find_child`,
  reads the row rect via virtual `[r8+0xC0]` into `[rsi+0x238]` and
  visibility via 0xEDBB50 into `[rsi+0x249]`.
- Its vtable is at file 0x13A1B50 (RVA 0x13A3350): binder, then 0x63C670
  (event handler; message 0x7E8 stores one int into the `[rsi+0x258]`
  array), menu-module 0xEDxxxx slots, 0x63DE80/0x63DF90. The formatter's
  table argument (RVA 0x13A3318) sits 0x38 bytes before it — possibly the
  same vtable's earlier slots (binder would be slot 7). Unconfirmed.
- Dialog names (`list_main`, …) have no LEA users anywhere: dialogs are
  addressed by other means; node names are the string path in.
- Evidence: scratchpad `ui728/names.py`, `callers.py`, `func_list.txt`,
  `func_sib.txt`, `callers.txt`.

## Binder triage (static)

- Tab strips (`I01_tab_select`, `S02_tab_select`) use `tab_cursor0_N`
  nodes, not `button%d_0`. `list_insert` shares `list_main`'s 14-row
  `buttonN_0` scheme. `data_list` uses yet another scheme: `list0..N`
  Dialog rows, 80 units tall.
- The dynamic-name binder family (formatter 0xC5C00, `find_child`, row
  rect via `[r8+0xC0]`, visibility via 0xEDBB50) spans 0x63C2C0 (calls
  0x63CF10 and 0x65E8A0, same shape) and 0x6615A0. 0x63C2C0's table
  neighbor is `tab_cursor`, so it may serve tabs; the button-row binder
  for `list_main` is one of its siblings — to be confirmed dynamically.
- 0x64DA90 and 0x659D00 are a different family (0xEF640, no formatter).
- Evidence: scratchpad `ui728/triage.py`.

## Live screenshot: the weapon list is data_list, not list_main

Lexer's weapon-change screenshot shows FIVE tall rows (icon + name +
six stat columns, e.g. 200/0/0/0/99/5.0), a left scrollbar and LB/RB
tabs — not the 14 text rows of `list_main`. The container is
`data_list`: BG + `list0`..`list4` Dialog row hosts + `Equip_line_1..8`
separators + frame. Each row hosts a `list_arms`-family instance. So
visible row count (5) is layout-driven; the exe formats rows with the
wide `list%d` string and navigates them through the Equip list classes.
The `list_main` two-column scaffold stands for the name-only menus; the
weapon grid is a second, `data_list`-based layout. Evidence:
scratchpad `ui728/` captures + `audit_dialogs.txt`.

## RTTI map: every dialog class with its vtable (static)

This build's RTTI uses 32-bit RVAs (COLA = sig/off/cd + typeDescRVA +
classRVA; vftable slot -1 holds the COLA VA). `ui728/rtti.py` maps
175/176 `FrpgMenuDlg*` classes; warp's vftable `0x13C6C40` matches 729's
anchor exactly. Attribution of the triage set:
`0x63C2C0`=`EquipListTab[27]`, `0x63C670`=`EquipListTab[28]`,
`0x63DE80`=`EquipListTab[37]`, `0x634A40`=`EquipList[16]` (row binder),
`EquipList` cursor candidates `[27]=0x634C40` (event dispatcher: msgs
0x3E9/0x3EC/0x3ED/0xA28/0xA2A/0x1388), `[35]=0x634EB0`,
`[36]=0x636CC0`, `[38]=0x635200`. Slot 40 (`0x6615A0`) is SHARED by all
list dialogs (Listbox, Warp, Inventory, shops…): a per-row updater that
formats the row name from dialog+0x210/+0x214 through formatter
`0xC5C00`, resolves container + row via `find_child`, attaches content
(`0xEDFAD0`) and sets visibility. Not vtable slots (plain helpers):
`0x63CF10`, `0x64DA90`, `0x659D00`, `0x65E8A0`. Ruled out as the listN
loop: `0x652FB0` (no row addressing inside). Full tables + lead-slot
disassembly: `ui728/vtables.txt`, `ui728/slots_*.txt`, `ui728/attr.py`.

## DS3/DS2: settled via 729, no duplication

729's commit `508390f6` (branch `ds1-729-warp-ui`) reports the finished
decryption: DS3 menus are Scaleform GFX in encrypted BDTs (BinderTool),
so nothing transfers as files to DRB; DS3 travel is a 14-row list with
per-row icons and L/R tabs (pattern only); DS3's exe is DRM-scrambled
(strings/RTTI only — the 142 `FrpgMenuDlg*` classes mirror DS1's 176);
DS2 is an unrelated Fe framework. 728 follows the same conclusion: DS3
icon-grid + 2D cursor + detail pane is design reference; all
implementation is DS1-native. No re-extraction needed.
