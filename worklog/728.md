# 728 — UI Rework (DS1 grid-style lists)

Owner: Muse (branch `ds1-728-ui-rework`, worktree `lexeditor-728`).
Issue scope: audit DS1's cramped list UIs, identify DS2/DS3 grid patterns,
recreate them in DS1 behind a tweak, preserving behavior.

## What the audit found (evidence in scratchpad `ui728/`)

- DS1 list screens are 14-row text lists: `list_main` / `list_category` /
  `list_insert` hold `button0_0`..`button13_0` (dynamic text, 30 units apart)
  plus `cursor0_0`..`cursor13_0` highlight rects. `audit_geometry.txt`.
- Row-content templates (`list_arms`, `list_armor`, `list_item`,
  `list_magic`, `list_arrow`) are single name-plus-stat-column layouts the
  exe instantiates per row; the exe references those dialog names as wide
  strings, and formats row names with `button%d_0` / `cursor%d_0`.
- `T02_equip_list` (equipment loadout) is already a 2D icon-button grid with
  exe-driven 2D navigation — not a rework target.
- DS2 is NOT available: both installs on D: are gutted (0 bytes besides a
  config). DS3 is present (24.8 GB) but packed in Data0-5/DLC `.bdt`/`.bhd`
  archives with no extractor on this machine, and its menu tech differs
  anyway. So "copying from DS2/3" reduces to design reference; all
  implementation is DS1-native.

## Technical conclusion

A working grid needs two things: (1) reposition existing row nodes in the
DRB layout, (2) exe patches to list navigation (2D cursor, scroll stride).
(1) is done on this branch: `menu_layout.py` moves plus the `ui-rework`
scaffold (28 moves, `list_main` column-major). (2) is next: find the
`button%d_0` user (capstone-assisted RE), loop bound and cursor math.

## Navigation RE findings (static, RVAs in the fingerprinted exe)

- `find_child` 0xED6020 has 1,182 call sites; the name arrives via
  `lea rdx` (832 static names incl. `cursor0_0`..`cursor5_0`,
  `button0_0`..`button5_0`, `scrollbar`, `list_cursor`) or stack-built
  (123 dynamic sites, incl. a 0x63Cx cluster). 227 pass it in a register.
- Row binder 0x63C2C0 (no direct callers; virtual): formats a dynamic node
  name through 0xC5C00 with the row index in r8d, calls `find_child`,
  reads the row rect via virtual `[r8+0xC0]` into `[rsi+0x238]` and
  visibility via 0xEDBB50 into `[rsi+0x249]`.
- Its vtable is at file 0x13A1B50 (RVA 0x13A3350): binder, then 0x63C670
  (event handler; message 0x7E8 stores one int into the `[rsi+0x258]`
  array), menu-module 0xEDxxxx slots, 0x63DE80/0x63DF90. The formatter's
  table argument (RVA 0x13A3318) sits 0x38 bytes before it — possibly the
  same vtable's earlier slots (binder would be slot 7). Unconfirmed.
- Dialog names (`list_main`, …) have no LEA users anywhere: dialogs are
  addressed by other means; node names are the string path in.
- Evidence: scratchpad `ui728/names.py`, `callers.py`, `func_list.txt`,
  `func_sib.txt`, `callers.txt`.
