# #100: Finish record-based mod combining

[Live GitHub issue and comments](https://github.com/Lexer-Lux/Lexeditor/issues/100)

## Requirements and decisions

Independent edits from enabled mods must coexist. When two mods edit the same proven record field, the later/higher-priority mod wins that field without discarding unrelated edits from the lower-priority mod.

## Current implementation and evidence

`plugins/ff8/runtime_layout.py` composes fixed-data files through the semantic merger in `plugins/ff8/fixed_data_merge.py` when an extracted baseline is available. The existing load-order verifier covers managed order, Hext order and conflict presentation.

Issue #100 now also has `tools/prepare_ff8_mod_combining_fixture.py`, which generates two ordinary folder mods from the user's own extracted `menu/price.bin`; no game data is committed. The fixture makes independent Hi-Potion/Phoenix Down edits and a deliberate Potion collision. `tools/verify_ff8_mod_combining_issue_100.py` composes both load orders from a synthetic baseline and verifies that independent fields coexist, only the Potion collision changes with priority, untouched bytes remain baseline-identical, and the conflict manifest names the correct winner/claimants.

GitHub Actions run 34062240051 passed both the pre-existing mod-order verifier and the new semantic fixture verifier on the branch.

## Format coverage audit (24 September 2026)

`plugins/ff8/runtime_layout.py` composes one complete file per logical path. It
tries a semantic merger for the path. If no merger applies, or the merger
declines the file, the last enabled mod wins the whole file and the result
reports the reason as an opaque winner.

| Logical path | Merger | Evidence |
| --- | --- | --- |
| `direct/kernel.bin` | `kernel_merge.merge` | `verify_ff8_kernel_merge.py` PASS |
| fixed-data specs (prices and similar) | `fixed_data_merge.merge` | `verify_ff8_fixed_data_merge.py` PASS |
| `direct/menu/mngrp.bin` | `mngrp_merge.merge` | `verify_ff8_mngrp_merge.py` PASS |
| world `wmx.obj`, `wmsetus.obj`, `rail.obj`, `texl.obj` | `world_data_merge.merge` | `verify_ff8_world_data_merge.py` PASS |

| field `*.jsm` scripts | `field_scripts.merge` | `test_ff8_mod_composition.py` PASS |

`pytest tests/ff8/test_ff8_mod_composition.py -q` -> 14 passed. Each merger also
declines the file and reports a reason when it meets bytes it cannot account
for, so an unknown format degrades to the opaque winner instead of corrupting a
file.

## Shared mod library integration (25 September 2026)

The header's mod selector said "Mod management is not supported for this game
yet" for FF8 while the library and the composer already shared one folder
layout. `plugins/ff8/mod_support.py` is the adapter that joins them: it
accepts an FF8 mod folder, enables the chosen library mods through the same
`configure()` the Mods tab uses, and composes the runtime in one step. It
writes only the library metadata and Lexeditor's own runtime tree, never the
game installation. `core/desktop_host.py` gives an adapter the selected
project and the library root through an optional `attach_context()`.

Evidence: `tests/ff8/verify_ff8_mod_library.py` (inspect, enable, compose,
disable, stored flags, game folder untouched). FF8 gate unchanged at its
pre-existing failure set.

Still Lexer's to confirm, together with the shop test above: a mod imported
from the header's mod library reaches a running game.
