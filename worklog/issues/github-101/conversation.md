## comment 5550107654 — Lexer-Lux

**Two answers from your log, one of them probably the whole thing.**

**First, the "no way to activate it anymore" part.** Committing an activation requires three things together: the pending request, a lit fire, and Rockstar's own `player_camp` script being referenced. Every presence line in your session reads:

```
presence begin site=3 activated=0 physical=0 trackedThread=0 refs=0
```

`refs=0`, every time. That is `player_camp` not referenced — so even a correctly made activation request cannot commit, and the site stays inactive forever. `activated=0` appears in all 22 samples; nothing activated at any point in the session.

**Second, and this is why it kept getting misdiagnosed:** nothing recorded whether the activation prompt was ever *shown*. Its visibility is an AND of five conditions — within 5 m, a physical fire present, not already activated, no request pending, and player control on — and none of them were logged. So "the prompt never appeared" and "the prompt appeared and the hold never completed" produced identical logs, and every previous attempt here was guessing between them.

That is fixed. Whenever you are within 25 m of a site it now logs each term separately:

```
activation prompt site=N canActivate=0/1 distance=… inRange=… physicalFire=…
  alreadyActivated=… pending=… playerControl=… playerCampRefs=…
```

So next time it will say outright whether the prompt was up, and if not, which condition killed it. If `canActivate=1` and nothing happens when you hold, the prompt works and the commit is being stranded on `playerCampRefs=0` — a different fix from the prompt not appearing at all.

**One thing that is deliberate, not a bug:** campsite status messages never appear on screen. They log as `status ui=omitted reason=unsafe-show-tooltip`. That helper crashed RDR2 inside an undocumented feed ABI — there is a retained crash trace naming it at the exact access violation — so it is permanently log-only.
